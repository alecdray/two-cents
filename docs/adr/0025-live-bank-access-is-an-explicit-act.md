# Reaching a live bank environment is an explicit act

`PLAID_ENV` **defaults to sandbox**, an unrecognised value **refuses to start**, and only the literal `production` resolves to the production host. Alongside it, the e2e suite aborts in global setup unless the server it is driving reports the deterministic fake provider ([ADR-0006](0006-bank-provider-selected-by-config.md)). Nothing reaches a real bank login by omission, typo, or forgetting which terminal a server was started in.

**The default was production, and that turned an omission into live access.** An unset `PLAID_ENV` almost always means a fresh checkout, a test harness, or a shell that never loaded the deployment's environment — none of which should be talking to anyone's bank. This is not hypothetical: an e2e run against a server started from a bare `.env` opened live Plaid Link a dozen times per run and sent the operator real OTP texts, because Plaid recognised the fixed `client_user_id` the app sends on every link-token request. The production host was reachable from three separate defaults (the config value, the origin mapper's fallback arm, and the client's default origin), so flipping any one of them alone would have changed nothing.

**An unknown environment is refused rather than resolved,** because both available fallbacks are wrong in opposite directions: falling back to production reaches real logins on a typo, and falling back to sandbox leaves a live deployment quietly talking to an environment holding none of its data. A startup panic is the only outcome that cannot be mistaken for working. For the same reason the deployment must name its environment out loud — the compose file supplies no default on either side.

**The test-suite interlock is not redundant with the default.** An operator's own `.env` legitimately names production, and the suite drives the connect control, which in real mode opens live Plaid Link against whatever the server was started with. The suite cannot choose the provider — the app runs as a separate process, deliberately — so the only move available to it is to refuse to proceed. It reads the mode the server rendered rather than its own `BANK_PROVIDER`, because the environment the test process sees is not necessarily the one the server was launched with, which is exactly how the two drift apart.

Consequence: a deployment that relied on the old implicit production default now fails to start until `PLAID_ENV` is set. That is the intended direction — a loud failure at boot, rather than a live instance nobody declared or a silent move to a sandbox with none of the real data.
