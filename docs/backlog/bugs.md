# Bugs

Known bugs, regressions, and tech debt. Architectural violations are tracked separately in [`../architecture/known-gaps.md`](../architecture/known-gaps.md).

- **Two of the sync pass's four error-collection sites are untested.** `SyncTransactions` collects failures from four places ([ADR-0021](../adr/0021-fault-isolating-sync-pass.md)); the accounts stage and the per-connection pull are pinned by tests, the **categorize sweep** and **transfer pairing** are not. Not a defect — all four are the same `errs = append(...)` shape and behave correctly — but nothing would fail if a refactor flipped either back to `return err`, silently restoring the abort-the-whole-pass behaviour this ADR removed. Closing it needs a seam: `transactions` holds `categorization` as a concrete `*categorization.Service`, so a failure cannot be injected without introducing an interface (the alternative, sabotaging the DB mid-pass, is contrived enough to be its own maintenance problem). Deliberately deferred out of the production fix rather than smuggling a design change into it.
- **Flaky e2e** `transaction-categorization.spec.ts:67` ("manual re-categorization survives a later sync") — an htmx `selectOption → waitForResponse` race; predates the budget slices. Suite is green with `--retries=2`. Candidate for `/diagnose`.
- **Manual categorization / transfer overrides can be lost on pending → posted.** Sync assumes a transaction moves pending → posted *in place* (same provider id), so override facets survive (they're excluded from the upsert). But when an institution reissues a **new** provider id for the posted transaction (Plaid links the two via `pending_transaction_id`), the pending row is deleted via the `removed` set and the posted row arrives as a fresh `added` row — so a manual re-categorization (and any transfer-destination override) is silently dropped and the posted row re-categorizes from scratch. Fix candidate: when applying an `added` row carrying a `pending_transaction_id`, carry the superseded pending row's override facets forward.
- **`PartialFlag` under-flags** later-added connections' backfill-edge months (correct for the common single-connection case; a precise history window is a [feature candidate](features.md)).
- **Disconnect hard-deletes accounts** instead of the domain's terminal `closed` state (a dangling transfer-destination FK) — tracked in [`../architecture/known-gaps.md`](../architecture/known-gaps.md).
- **Archetype and convention slips predating the occurrence-matching slice.** Surfaced by that branch's pre-merge audit and left out of it to keep the diff scoped; none has a functional consequence. Archetype-level: `plaid/logo.go` holds raw outbound HTTP outside `client.go`, which the [external-client archetype](../architecture/archetypes/external-client.md) does not allow for (either fold it into `client.go` or document the deviation in `plaid/AGENTS.md` the way `fakebank` does); `home` declares seven view models in `service.go` with no `home.go` topic file; and `transactions/adapters/transactions_page_test.go` imports `accounts/adapters/views`, the peer-`adapters` import only the composition root may make (the assertion belongs in `server/assembled_test.go`). Naming: `home/adapters/views/month_rail.templ` carries no archetype suffix, `categorization`'s `RuleEditorReturnLoader` no `Frag` suffix, and `budget`/`categorization` each hold a `shared.templ` naming no surface. If these are not cleared soon the three archetype-level ones should graduate to [`../architecture/known-gaps.md`](../architecture/known-gaps.md) entries of their own.
- **A connection whose access token will not decrypt cannot be disconnected.** `accounts.Disconnect` (`src/internal/accounts/service.go:446`) resolves and decrypts the stored token, then calls the provider's `RemoveItem`, and only then deletes the local accounts and connection rows. Both steps precede any local cleanup, so either one failing leaves the connection in place with no in-app way to remove it — the UI surfaces a 500 and the row survives every retry. Observed with a token that would not decrypt (`failed to decrypt access token: illegal base64 data at input byte 5`); the realistic trigger is a rotated `ENCRYPTION_KEY`, which invalidates every stored token at once and would strand *all* of a user's connections, undeletable, while the same error also fails their syncs. Recovery today is manual SQL. Fix candidate: treat the provider call as best-effort for a *disconnect* specifically — the user's stated intent is removal, so a token that cannot be decrypted or an item the provider has already dropped should still delete the local rows, with the orphaned provider item reported rather than blocking. Worth deciding deliberately: it trades a possible orphaned item at Plaid for a local state the user can always escape.
