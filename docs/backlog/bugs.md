# Bugs

Known bugs, regressions, and tech debt. Architectural violations are tracked separately in [`../architecture/known-gaps.md`](../architecture/known-gaps.md).

- **Two of the sync pass's four error-collection sites are untested.** `SyncTransactions` collects failures from four places ([ADR-0021](../adr/0021-fault-isolating-sync-pass.md)); the accounts stage and the per-connection pull are pinned by tests, the **categorize sweep** and **transfer pairing** are not. Not a defect — all four are the same `errs = append(...)` shape and behave correctly — but nothing would fail if a refactor flipped either back to `return err`, silently restoring the abort-the-whole-pass behaviour this ADR removed. Closing it needs a seam: `transactions` holds `categorization` as a concrete `*categorization.Service`, so a failure cannot be injected without introducing an interface (the alternative, sabotaging the DB mid-pass, is contrived enough to be its own maintenance problem). Deliberately deferred out of the production fix rather than smuggling a design change into it.
- **`WithTx` hands back a `*DB` whose `Sql()` escapes the transaction.** `core/db.DB` holds both the connection pool and the sqlc query set, and `newDBWithTx` rebinds only the query set — so inside a `WithTx` callback `tx.Queries()` runs in the transaction while `tx.Sql()` silently runs on a *different pooled connection*. Both compile on the same `*DB`, and the parameter is conventionally named `tx`, so nothing signals the difference. **Not a defect today:** `Sql()` has zero non-test callers, and all five production callbacks do only `NewRepo(tx.Queries())`. The hazard is a future one, and asymmetric — a *read* through `tx.Sql()` silently misses the transaction's own uncommitted writes (wrong answer, no error), whereas a *write* mostly fails loudly, contending for the write lock the transaction holds until `_busy_timeout` expires. It stays unsprung only by convention (`repo.go` is the sole sqlc importer, and no production code uses raw SQL at all), which is exactly the kind of guarantee the type system should be making instead. Fix candidate: give `WithTx` a distinct parameter type exposing only `Queries()` — cheap precisely because every callback already uses only that, so the change is the parameter type and nothing else. The `DB` doc-comment ("reads and writes share the transaction's view") should be narrowed in the same change; it is the sentence most likely to convince someone `tx.Sql()` is safe.
- **`task test/unit` fails `core/app` config tests, and prints the real Plaid secret.** `taskfile.yml` declares `dotenv: [.env]`, so `task` injects the live environment into the test process and `config_test.go` reads the real `PLAID_SECRET`/credentials instead of its fixtures — two assertions fail and the actual secret is echoed into test output (and thus into any captured log or CI artifact). `go test ./src/...` passes, so the gate only fails through `task`. Fix candidates: have the config tests isolate their environment (`t.Setenv` / clear the relevant vars), or drop `dotenv` from the test task.
- **Flaky e2e** `transaction-categorization.spec.ts:67` ("manual re-categorization survives a later sync") — an htmx `selectOption → waitForResponse` race; predates the budget slices. Suite is green with `--retries=2`. Candidate for `/diagnose`.
- **Manual categorization / transfer overrides can be lost on pending → posted.** Sync assumes a transaction moves pending → posted *in place* (same provider id), so override facets survive (they're excluded from the upsert). But when an institution reissues a **new** provider id for the posted transaction (Plaid links the two via `pending_transaction_id`), the pending row is deleted via the `removed` set and the posted row arrives as a fresh `added` row — so a manual re-categorization (and any transfer-destination override) is silently dropped and the posted row re-categorizes from scratch. Fix candidate: when applying an `added` row carrying a `pending_transaction_id`, carry the superseded pending row's override facets forward.
- **`PartialFlag` under-flags** later-added connections' backfill-edge months (correct for the common single-connection case; a precise history window is a [feature candidate](features.md)).
- **Disconnect hard-deletes accounts** instead of the domain's terminal `closed` state (a dangling transfer-destination FK) — tracked in [`../architecture/known-gaps.md`](../architecture/known-gaps.md).
