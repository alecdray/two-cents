# accounts — domain module

Rules: ../../../docs/architecture/archetypes/domain-module.md

Module-specific notes:
- Provider-agnostic: reaches the bank only through the injected `banking.BankProvider` seam and `banking.ErrReauthRequired`. It must never import `plaid` (enforced by `architecture/isolation_test.go`).
- `repo.go` is the only file that touches `core/db/sqlc`; its methods take and return this package's domain types (`Connection`, `Account`), never `sqlc.*`.
- Access tokens are encrypted at rest via `core/cryptox` under the config encryption key; the plaintext is never persisted unencrypted, never sent to the client, and is never stored on the `Connection` entity. It may be handed to the in-process `transactions` sync via `ConnectionsToSync` (decrypted inside this service, the field's owner).
- Seeding (`SeedAccountKind` / `SeedCountsAsSavings`) runs only when an account first appears. Sync refreshes balance + last-synced and discovers new accounts, but never reseeds an existing account's kind/counts-as-savings, nor duplicates it.
- **`SyncAccounts` isolates per-connection failures** ([ADR-0021](../../../docs/adr/0021-fault-isolating-sync-pass.md)): every active/needs-reconnect connection is attempted regardless of what the others do, each failure is tagged with its connection + item id and collected, and the joined error is returned at the end. A `banking.ErrReauthRequired` still flips the connection to needs-reconnect and is not an error; any other failure leaves the connection's **state unchanged** so the next tick retries it. So a non-nil return means "some connection failed", not "nothing synced".
- **Balance staleness is a read-model fact, derived not stored** ([ADR-0021](../../../docs/adr/0021-fault-isolating-sync-pass.md)). `Account.BalanceStale` is the **one definition** of the question and this module owns it; the threshold and its justification live in `staleAfter`'s doc-comment beside it, the term in the [domain glossary](../../../docs/domain/README.md). Callers ask this module rather than carrying their own threshold — a second one anywhere would be free to drift from this one. `Stale` and `NeedsReconnect` are **independent** — the view chooses which to show when both hold; the service does not suppress either.
- **Statement detail refreshes inside the existing pass, never on its own schedule.** `SyncAccounts` reads card statements through the seam in the same per-connection attempt as balances, under the same fault isolation — a connection whose statement read fails leaves its stored detail untouched and does not deny the others their refresh. It is fetched **only for connections holding at least one active credit Account**, so a cash-only login makes no such call. It inherits the same `last_synced_at` stamp, which is what keeps `BalanceStale` the one staleness rule rather than growing a second for statements.
- **An unreported statement field stays unknown.** Statement balance, issue date, and due date are each independently nullable and are never defaulted — the sweep's missing-data rule turns an unknown into the *worst* case (the whole balance due immediately), so writing a zero or a today would silently make the answer less conservative rather than more.
- **`SetPaymentSchedule` is a user override like kind/savings**, and the only per-account facet that is a statement *about* the card rather than a fact from it. The default is the reported due date; the alternative is a fixed offset from the statement issue date. Sync never touches it. The default is deliberately the optimistic branch — a due date is an upper bound, since autopay can only pull earlier — which is a decision ADR-0024 records and accepts, not an oversight to fix here.
- `SetAccountKind`/`ToggleCountsAsSavings` are the user overrides (mark the account overridden so sync won't reseed). **`SetAccountKind(…, credit)` force-clears `counts-as-savings`** — the one coupling between the two otherwise-orthogonal axes, because the transfer-subtype engine assumes a credit destination's flag is false ([ADR-0008](../../../docs/adr/0008-account-kind-and-savings-overrides.md)). Each method reports whether the effective `counts-as-savings` value changed; the adapter (not the service) fires the re-pair seam on a real change. The service never imports `transactions`.
- The override re-pair is an injected seam mirroring the connect/reconnect `BackfillTransactions` hook: wired at the composition root to the transactions re-pair, called by the adapter after an override that changed the flag, a nil hook skips it. A `cash`↔`other` kind change leaves the flag untouched and triggers no re-pair.
- The overview totals (net cash, free cash, total savings, total cash, total debt) are computed over active (non-hidden/non-closed) accounts only; an unknown balance is excluded, never counted as zero. Total savings is the counts-as-savings slice of `cash`; free cash = net cash − total savings. **`HideAccount`/`UnhideAccount`** move an account between `active` and `hidden` and trigger no re-pair — a hidden account leaves the overview and the `ConnectedAccountFacets` pickers, but its transactions keep counting.
- `SetAccountName` sets/clears the nullable `custom_name` (the override is the column being non-NULL — no flag, unlike kind/savings); input is trimmed + capped at 60 chars, empty clears back to the bank `name`. `Account.DisplayName()` is the sole precedence point (`custom_name` else `name`); the overview rows and `ConnectedAccountFacets` use it, so the transactions picker + transfer-pairing inherit the custom name. `DisplayNames(ctx, ids)` is the read seam other modules use to name accounts they hold only the id of (it spans every state, not just active like the facets) — so the transactions activity read resolves account/destination names here instead of joining `name` in SQL, keeping the precedence owned by this module. Sync refreshes `name`, never `custom_name`. A rename touches no kind/savings axis, so it fires no re-pair ([ADR-0017](../../../docs/adr/0017-custom-account-names.md)).
- The overview at `/accounts` surfaces the whole connection lifecycle — connect, disconnect (confirmation-gated, deletes the bank's accounts + connection), reconnect (update mode, clears `needs_reconnect`) — plus the per-row kind picker + counts-as-savings toggle (toggle on `cash`/`other` rows only) and a one-click hide control (hidden accounts collect in a separate Hidden section with an unhide control), each swapping the shared overview region. Recoverable failures render inline (connect error in the control; reconnect error beside the row); never redirect.
- Disconnect is a server action in both bank modes (no provider modal); reconnect mirrors connect's dual mode (fake posts directly, real runs the Alpine relink-token interceptor). Failures during reconnect leave the connection `needs_reconnect`. The kind/savings override and hide/unhide are server actions in both modes.
- e2e (`BANK_PROVIDER=fake`) covers connect/disconnect/reconnect, the kind/savings override, hide/unhide, and the stale-balance mark against the real server. The fake holds one connection with all three accounts; reconnect e2e connects via the fake then flips `state` to `needs_reconnect` in SQLite so the stored token stays decryptable. The stale-balance scenarios age a seeded account via the seeder's `lastSyncedHoursAgo` (default 0, so every other seeded row stays fresh).
